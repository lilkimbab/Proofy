# 문제 생성 + 피드백 핵심 개념

이 문서는 구현 전에 꼭 알아야 할 개념만 남긴 요약이다. 상세 실행 순서는 [../problem-feedback-roadmap.md](../problem-feedback-roadmap.md)를 본다.

## 1. 우리 파트의 역할

사용자가 올린 자료에서 검색된 chunk를 받아 문제를 만들고, 사용자의 답안을 채점해 피드백을 제공한다.

직접 담당:

- 자료 기반 문제 생성
- 정답/해설/rubric 생성
- 객관식 코드 채점
- 주관식 LLM 채점
- 오답 유형과 약점 개념 추출
- 복습 추천과 다음 행동 제안

직접 담당하지 않음:

- PDF 파싱
- OCR/vision
- Vector DB
- RAG 내부 검색
- 사용자 계정 DB
- 전체 학습 로드맵

## 2. 전체 흐름

문제 생성:

```text
요청 검증
→ Search/RAG에서 근거 chunk 조회
→ ProblemAgent가 문제 후보 생성
→ QualityChecker 검증
→ 통과 문제 저장
→ 제출 전 화면용 응답 반환
```

답안 제출:

```text
답안 저장
→ 문제와 근거 조회
→ 객관식은 코드 채점
→ 주관식은 rubric 기반 LLM 채점
→ Feedback 저장
→ UserConceptStat 업데이트
→ 피드백 반환
```

## 3. 핵심 설계

### RAG

LLM이 아무 지식이나 쓰지 않도록, 검색된 자료 chunk만 문제 생성과 피드백 근거로 사용한다.

### Structured Outputs

LLM 출력은 자유 문장이 아니라 정해진 JSON Schema로 받는다. 필드가 빠지거나 형식이 틀리면 저장하지 않는다.

### Quality Gate

문제 저장 전 최소 품질을 검증한다.

- source chunk 존재
- 정답이 보기 안에 있음
- 보기 4개
- 주관식 rubric 존재
- 자료 밖 수치/조건 생성 방지
- 원문 장문 복제 방지

### User Model

정답/오답 결과를 개념별 mastery로 반영한다.

- 정답: `+0.05`
- 오답: `-0.08`
- 범위: `0.0 ~ 1.0`
- 같은 개념 반복 오답이면 복습 추천

## 4. 모델 사용 기준

기본 방향은 비용 효율이다.

- 객관식 채점: LLM 사용 안 함
- 객관식 피드백: 기본 템플릿
- 일반 문제 생성: 비용 효율 모델
- 주관식 채점/고난도/엄격 검증: 상위 모델

실제 모델명과 토큰 제한은 `.env.example`와 [../README.md](../README.md)를 따른다.

## 5. 사용자 문체

문제 자체는 시험 문제처럼 간결하게 쓴다.
피드백은 친근한 존댓말을 쓴다.

나쁜 예:

```text
오답입니다. 이해도가 부족합니다.
```

좋은 예:

```text
여기서 헷갈린 건 원인과 결과의 순서예요.
자료에서는 A가 먼저 나오고, 그 다음 B가 이어진다고 설명해요.
순서를 표시하면서 다시 풀어볼까요?
```

## 6. 꼭 지킬 것

- 사용자의 자료를 다른 사용자 문제 생성에 재사용하지 않는다.
- 업로드 자료를 모델 학습 데이터로 쓰지 않는다.
- 문제/해설이 원문을 길게 베끼지 않게 한다.
- Search/RAG가 실패하면 애매하게 생성하지 않고 실패를 명확히 반환한다.
- 실제 OpenAI 호출 테스트는 API key가 있을 때만 실행한다.
