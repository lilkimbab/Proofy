# 문제/피드백 문체 품질 전략

작성일: 2026-05-06

## 결론

지금 단계에서는 별도 모델 학습이 먼저가 아니다.

상업 서비스에서 바로 적용할 순서는 아래가 맞다.

1. 제품 문체 기준을 정한다.
2. 프롬프트에 그 기준을 넣는다.
3. 코드 품질 검증기로 어색한 표현을 걸러낸다.
4. 실제 사용자 반응을 보고 문체 예시를 쌓는다.
5. 충분한 데이터가 생긴 뒤에만 fine-tuning이나 선호도 학습을 검토한다.

## 기본 말투

기본 목소리는 `존댓말을 쓰는 친근한 교육자`로 둔다. 이 기준은 **피드백, 힌트, 재시도 안내, 오답 맞춤 콘텐츠 안내**에 적용한다.

문제 문항 자체는 예외다. 문제는 실제 시험지처럼 담백하게 작성한다.

문제 문항:

- 이모티콘을 쓰지 않는다.
- "우리", "해볼까요", "헷갈리셨군요" 같은 코칭 말투를 쓰지 않는다.
- 객관식은 무엇을 고르면 되는지 명확히 쓴다.
- 주관식은 "설명하시오", "분석하시오"처럼 요구 작업을 분명히 쓴다.
- 공식과 변수 관계는 LaTeX로 표기한다. 예: `$F = ma$`, `$a = F / m$`.

피드백:

- 존댓말을 유지하되 친근하게 말한다.
- 이모티콘을 상황에 맞게 쓴다.
- 학생이 바로 다음 행동을 선택할 수 있게 한다.

지켜야 할 기준:

- 해요체를 기본으로 쓴다.
- 학생을 평가하기보다 옆에서 같이 짚어주는 느낌으로 말한다.
- "우리 ... 해볼까요?"는 너무 자주 쓰지 않되, 다음 행동을 제안할 때 자연스럽게 쓴다.
- 오답은 "틀렸다"보다 "이 부분이 헷갈리셨군요"처럼 표현한다.
- 개선 설명은 "이렇게 하면 더 깔끔하답니다"처럼 부드럽게 안내한다.
- 칭찬은 "잘하셨어요"로 시작해도 되지만, 반드시 구체적인 이유와 연결한다.
- 이모티콘은 기본적으로 상황에 맞게 사용한다. 정답, 힌트, 반복 오답, 로딩처럼 감정 완충이 필요한 곳에 특히 효과적이다.
- 단, 근거 설명 문장마다 이모티콘을 붙이지 않는다. 핵심 설명은 신뢰감이 먼저다.

좋은 예:

- "좋아요, 잘하셨어요 👍 특히 조건을 놓치지 않고 보신 점이 좋아요."
- "이 부분이 헷갈리셨군요 🤔 자료에서는 A가 먼저 나오고, 그 다음 B가 이어진다고 설명해요."
- "우리 기준부터 천천히 잡아볼까요?"
- "힌트 하나만 드릴게요 💡 정답을 바로 보지 말고 기준만 같이 잡아볼까요?"
- "괜찮아요 😊 이 부분은 예시 하나로 보면 훨씬 깔끔해져요."

## 오답 유형별 피드백 방향

오답 피드백은 단순히 맞고 틀림만 말하지 않는다. `mistake_type`에 따라 다음 행동을 다르게 제안한다.

- `concept_misunderstanding`: 개념 방향을 다시 잡게 한다. 버튼: `개념 카드로 30초 복습`
- `missing_key_concept`: 빠진 조건을 채우게 한다. 버튼: `내 답 다시 써보기`
- `term_confusion`: 비슷한 용어를 비교하게 한다. 버튼: `비슷한 용어 비교하기`
- `calculation_error`: 풀이를 한 줄씩 나누게 한다. 버튼: `단계 나눠서 다시 풀기`
- `logic_error`: 원인과 결과를 연결하게 한다. 버튼: `단계 나눠서 다시 풀기`
- `misread_question`: 문제 조건을 표시하게 한다. 버튼: `조건 표시하고 다시 풀기`
- `incomplete_answer`: 답안을 보완하게 한다. 버튼: `내 답 다시 써보기`
- `unit_error`: 단위부터 점검하게 한다. 버튼: `단위만 체크하기`

## 왜 바로 학습부터 하지 않는가

학습 데이터 없이 fine-tuning부터 하면 제품 말투가 좋아지는 것이 아니라, 어색한 말투가 고정될 수 있다. 특히 학습 서비스에서는 말투보다 정답 정확성, 자료 근거, 채점 일관성이 더 중요하다.

초기에는 모델을 새로 학습시키는 것보다 아래 방식이 비용 대비 효과가 좋다.

- 금지 표현 목록
- 좋은 예시 문장
- 짧은 문장 규칙
- 내부 용어 노출 금지
- 품질 검증기에서 어색한 표현 차단

## 사용자에게 보이면 안 좋은 표현

피해야 할 표현:

- "자료에서 어떤 관계를 중심으로 설명되는가?"
- "핵심 개념을 확인하는 개념이다."
- "자료의 해당 부분"
- "가장 적절한 것은?"
- "설명하시오"
- "작성하시오"
- "기반으로"
- "수행한다"
- "제공한다"
- "관련된다"
- "활용한다"
- "루브릭"
- "청사진"
- "메타데이터"
- "chunk"
- "source"
- "LLM"

더 나은 표현:

- "무엇이 달라질까?"
- "어떤 점을 놓치면 헷갈릴까?"
- "이 조건에서는 어떻게 판단해야 할까?"
- "여기서 놓친 지점은 ..."
- "이 부분을 다시 보면 좋아."
- "같은 개념을 다른 조건으로 한 번 더 풀어보자."

## 코드 반영 내용

현재 반영된 파일:

- `app/agents/korean_style.py`
- `app/agents/problem_agent.py`
- `app/agents/feedback_agent.py`
- `app/agents/learning_content_agent.py`
- `app/agents/quality_checker.py`
- `app/agents/learning_content_quality_checker.py`
- `app/schemas/learning_voice.py`
- `app/services/learning_voice_renderer.py`
- `app/services/learning_copy_quality_checker.py`
- `tests/test_korean_style_quality.py`
- `tests/test_learning_voice_renderer.py`

반영된 정책:

- 공통 한국어 문체 가이드 추가
- AI스러운 템플릿 표현 탐지
- 내부 개발 용어 노출 탐지
- 학습 콘텐츠 품질 검증에서 어색한 문체 거부
- strict 문제 생성에서는 어색한 문체가 있으면 저장 거부
- deterministic fallback 문장 일부를 더 자연스럽게 수정
- 정답 구조와 사용자 표시 문장을 분리하는 `copy` 응답 계층 추가
- `FeedbackCopyInput`에서 의미 구조를 받고 `FeedbackCopyOutput`에서 화면 문구를 만든다
- 오답/부분 정답/반복 오답 문구에는 다음 행동 버튼 문구를 요구한다
- 사용자 화면에는 `LLM`, `chunk`, `schema`, `quality_status`, `Agent`, `API` 같은 내부 용어가 나오지 않게 검사한다

## 사용자 표시 문구 구조

문제, 정답, 해설, 채점 결과는 기존 필드에 그대로 둔다. 화면에서 바로 보여줄 문장은 별도 `copy` 필드에 둔다.

예:

```json
{
  "is_correct": false,
  "mistake_type": "concept_misunderstanding",
  "feedback": "정답 여부: 아직 정답은 아니야...",
  "copy": {
    "title": "원인과 결과의 순서가 조금 헷갈리셨군요 🤔",
    "body": "자료에서는 A가 먼저 나오고, 그 다음 B가 이어진다고 설명해요. 우리 기준부터 천천히 잡아볼까요?",
    "next_action_label": "힌트만 보고 다시 풀기"
  }
}
```

이렇게 나누는 이유:

- 채점/저장용 데이터는 구조를 유지한다.
- 화면 문구는 따로 검증하고 개선한다.
- 나중에 Personalization 파트가 붙어도 말투만 바꾸기 쉽다.
- 같은 피드백 의미를 초등/중등/고등/성인 말투로 바꾸기 쉽다.

## 앞으로 더 좋아지는 방법

1차 출시 전:

- 실제 PDF 5~10개로 사람이 보기 좋은 문제/피드백 샘플을 만든다.
- 좋은 문장과 나쁜 문장을 따로 모은다.
- eval set에 `말투 자연스러움` 항목을 넣는다.

서비스 운영 후:

- 사용자가 다시 질문한 피드백 문장을 수집한다.
- "이해됨/이해 안 됨" 반응을 피드백 품질 지표로 삼는다.
- 사용자별 말투 조정은 Personalization 담당 파트와 연결한다.

fine-tuning 검토 조건:

- 좋은 피드백 예시가 최소 수백 개 이상 쌓였을 때
- 금지 표현과 선호 표현이 안정적으로 정리됐을 때
- 프롬프트만으로 문체 품질이 더 이상 개선되지 않을 때

그 전까지는 프롬프트와 품질 검증기로 충분히 개선하는 것이 비용과 위험 면에서 낫다.
